一棵树，不是一份程序

你启动的不是一个写好的应用，是一棵现场拼出来的插件树。

预计 25 分钟 不需要写 JavaScript 结尾有可亲手验证的动作

读完能回答

  1. 启动时的插件树是由哪几层、按什么顺序叠出来的？
  2. profile、bundle、patch 三个词各指什么，它们分别在哪一层？
  3. 为什么「后来的一层」能改掉「先前的那一层」，改的粒度是什么？
  4. 你自己要写的东西，将来落在这一叠里的第几层？

一先看一棵真实的树

先不谈概念。打开你这台机器上的 web profile，让它把自己启动时的配置完整打印出来：

pwsh -NoProfile -File .\scratch\dsh.ps1 --profile web --dump-config

输出 1229 行 YAML。本机实测 里面是 190 个「行」（entry），每行长得像这样：

- id: timer
  name: '@deepseek-ai/cordis-plugin-timer'

就这么两行，说的是：「挂载 @deepseek-ai/cordis-plugin-timer 这个东西，给它起名叫 timer」。

展开一点看，很多行还带第三段：

- id: session-title
  name: '@deepseek-ai/dsh-session-title'
  config:
    fallbackMaxWords: 5
    fallbackMaxBytes: 40
    maxTitleBytes: 80

这里 config 是交给那个插件的参数——插件被挂载时会收到它，据此决定自己怎么工作。上例说：标题兜底最多 5 个词、40 字节，最终上限 80 字节。

用你熟的 C++ 说

每一行相当于一条写在配置文件里的「加载指令」：name 是 DLL 路径，config 是这个模块自己的启动参数结构体。整个 dump-config 输出就是启动时要按顺序处理的一整张加载表。

关键一点

这 190 行不是从某个源文件里读出来的常量表。它们是现场算出来的。这就是本课的全部内容。

二三个词：profile / bundle / patch

树的来源只有三个概念，先把它们钉死。

profile（配置档）

一个命名的组合，存在你的家目录里。它做三件事：

  • 列出一串要叠上去的 bundle（有序，顺序有意义）
  • 存自己的 cordis.patch.yml（你的补丁层）
  • 存装进来的第三方插件的依赖声明

你现在用的叫 desktop。它的清单在 ~/.dsh/profiles/desktop/package.json，本机实测 列了 15 个 bundle，其中 6 个是 @deepseek-ai 官方包，剩下 9 个来自别处（dsh-whale-widget、dshmarket 这些）。

{
  "name": "dsh-profile-desktop",
  "dependencies": { "dsh-whale-widget": "^0.4.2", ... },
  "dsh": {
    "profile": {
      "bundles": [
        "@deepseek-ai/dsh-base",
        "@deepseek-ai/dsh-web-app",
        "dshmarket",
        ...
      ]
    }
  }
}

出处：~/.dsh/profiles/desktop/package.json（节选）

bundle（组合包）

一个 bundle 就是一个 npm 包，它的 package.json 里多了一个 dsh 字段，指向一份 patch 文件：

{
  "name": "dsh-whale-widget",
  "dsh": { "bundle": { "patch": "./cordis.patch.yml" } }
}

出处：~/.dsh/profiles/desktop/node_modules/dsh-whale-widget/package.json（节选）

就这一行声明，让它成为 bundle。没有 dsh.bundle.patch 的包只是普通依赖，不是插件。

patch（补丁层）

patch 是一棵 YAML 数组，每个元素是一条「动作」。只有两种动作：

形态含义
- insert: + 行数组往树里插入若干新行
- id: xxx + 字段覆盖一个已存在的行（按 id 找）
已经能看出来了

这三件事环环相扣：profile 按顺序列出 bundle，每个 bundle 贡献一份 patch，patch 往同一棵树里插行或改行。没有哪一份文件单独描述整棵树；树是它们叠起来的结果。

三叠的顺序：后来者赢

官方文档写得很直白 官方文档：

Layers apply to an empty entry list: the profile's ordered bundles, its cordis.patch.yml, the home patch, then --patch overlays.
—— docs/architecture.md

翻成人话，从底到顶是这样五步：

  1. 从一张空表开始——不是从某个默认配置开始，是空。
  2. 按 bundles 数组的顺序，把每个 bundle 的 patch 依次叠上去。
  3. 叠该 profile 自己的 cordis.patch.yml。
  4. 叠家目录级的 ~/.dsh/cordis.patch.yml（你这台机器上不存在这个文件，所以这层是空的 本机实测）。
  5. 叠命令行上每个 --patch 指定的文件，从左到右。

我用两次 --patch 实测了这个顺序 本机实测。第一层插一行，第二层用同一个 id 去改它：

# layer-1.patch.yml
- insert:
    - id: layer-experiment
      name: 'layer-experiment-not-a-real-module'
      config:
        who: first-layer
        color: blue

# layer-2.patch.yml
- id: layer-experiment
  name: 'layer-experiment-not-a-real-module'
  config:
    who: second-layer

跑 --patch layer-1 --patch layer-2 --dump-config，树里那一行变成：

# == N:\...\layer-1.patch.yml, patched by N:\...\layer-2.patch.yml
- id: layer-experiment
  name: layer-experiment-not-a-real-module
  config:
    who: second-layer

出处：本机 --dump-config 实际输出（第 1230 行起）

三个信息同时成立：

  • 后叠的层赢了：who 是 second-layer。
  • 但那一行没有变成两行——它还是同一行，被就地改写了。
  • 层注释直接写着 layer-1.patch.yml, patched by layer-2.patch.yml，谁改了谁一目了然。

四最容易踩的坑：覆盖是整体替换

上一步有个细节我故意没讲：color: blue 去哪了？

它没了。这就是这条路上第一个、也是最贵的坑。

坑

按 id 覆盖一个行的时候，config 是整体替换，不是逐键合并。你只给一个键，其余键全部消失。

我又单独验了一遍 本机实测，因为这条太反直觉。拿官方自带的一行开刀——它本来有三个键：

原来（base 层）
我覆盖时只给了 maxTitleBytes
config:
  fallbackMaxWords: 5
  fallbackMaxBytes: 40
  maxTitleBytes: 80
config:
  maxTitleBytes: 999

结果：前两个键整个消失，只剩我写的那个。

# == @deepseek-ai/dsh-base, patched by probe3.patch.yml
- id: session-title
  name: '@deepseek-ai/dsh-session-title'
  config:
    maxTitleBytes: 999

出处：本机 --dump-config 实际输出（第 32 行起）

所以规矩是：想改一个键，就把这一行的完整 config 抄一遍再改。这也是为什么官方 web-app 的 patch 开头要写那句话 源码实读：

A patch replaces the targeted row's whole config, so each row below restates every key it owns.
—— @deepseek-ai/dsh-web-app/cordis.patch.yml 第 5 行
顺带一个好消息：覆盖时可以不写 name

上面那次覆盖，我故意只写了 id 和 config，没写 name。dump 出来那一行仍然带着原来的 name。本机实测

所以覆盖时你只需要交代「改哪个键」，不用重复它是什么模块。但 config 还是要抄全——这两件事不一样。

五动手：往树里插一行

到这儿概念够了，轮到你亲手验一次。目标：让自己写的一层出现在 dump 里。整个过程不写一行 JavaScript，也不碰任何该保留的文件。

  1. 先看 baseline。在 teach 目录下跑：

    pwsh -NoProfile -File .\scratch\dsh.ps1 --profile web --dump-config

    记住结尾长什么样。最后一行大概是 tool-plugin-market 那个块。

  2. 新建一个文件 scratch\my-first-layer.patch.yml，内容三行：

    - insert:
    - id: my-first-row
      name: 'my-first-row-not-a-real-module'

    注意缩进：insert: 后面是一个列表，列表项比它多缩进两格。- 后面要有空格。

  3. 带上它再 dump 一次：

    pwsh -NoProfile -File .\scratch\dsh.ps1 --profile web `
  --patch .\scratch\my-first-layer.patch.yml --dump-config

  4. 在输出末尾找这一块：

    # == N:\DSH-Plugin-dev\teach\scratch\my-first-layer.patch.yml
- id: my-first-row
  name: my-first-row-not-a-real-module

    找到就是成功。那行 # == 是这一层的名字，它是你的。

为什么 name 指向一个不存在的模块也没事

因为 --dump-config 只做配置计算，不加载任何代码 本机实测。这让它成为一个完美的纯配置实验台：随便插假行，不影响任何东西，也不需要模块真的存在。

反过来说：真正启动时会失败。所以这条实验只在 dump 里做，别拿去启动。

这一步你得到了什么

你亲手证明了「层」是真实存在的、可插的、有名字的。你写的一个文件，和官方 dsh-base 的 patch，在树里是同一种东西——没有特权核心，只有先后顺序不同的层。

六那我要写的东西落在第几层

回到你的实际问题。你现在有三种可选做法，落在不同的位置：

做法落在哪适合什么阶段
--patch 临时一层 最顶层，只在本次启动有效 实验。改了重跑命令就行，不留痕。就是刚才你做的事。
改 profile 的 cordis.patch.yml 倒数第二层，长期有效 日常配置调整。但会被家目录层和 --patch 盖过。
做成 bundle 装上 由 bundles 数组的位置决定 真正交付。这是 dialog-box 要走的路，第七课讲。
为什么实验不要改 desktop profile 的 patch

那是你每天用的树，里面还有 dsh-skill-mcp-panel 自动维护的 MCP 区块。手改容易打架。用 web profile 做实验，它只有两个 bundle、干净、坏了也好恢复；而且 --dump-config 不写文件，连改都算不上。

七回到你的项目

你的输入框插件最终会是什么形态？现在可以给一个准确的答案了：

一个 bundle。它会往树里插自己的行，那些行指向你自己的模块。模块会在宿主进程里跑起来，向 ctx 注册能力；如果要做界面，还会有浏览器侧的一半，往界面预留的槽位里注册组件。

而这一切的前提，是你先知道自己插进去的行排在哪、被谁改过。否则出问题时你连查哪儿都不知道。

八自测

启动时的插件树，最初的样子是什么？
  • 一张预先写好的配置表，照着加载
  • 运行时扫描模块，动态推导出清单
  • 一张空表，按层顺序逐条叠加出来
  • 安装程序生成的快照，升级才刷新
按 id 覆盖一个已有行，只写其中一个 config 键会怎样？
  • 其余键被抹掉，只剩写出的那个
  • 其余键都保留，写出的键被替换
  • 整行被忽略掉，沿用原来的配置
  • 启动时报错，直接拒绝这次覆盖
下面哪一种顺序，跟实际的叠加顺序一致？
  • profile 补丁、bundle、--patch 层
  • bundle、profile 补丁、--patch 层
  • --patch 层、bundle、profile 补丁
  • bundle、--patch 层、profile 补丁
--dump-config 里写一个不存在的模块名，为什么能成功？
  • 因为模块名会被自动替换成默认值
  • 因为加载器会跳过所有未知的条目
  • 因为那条配置只在真正启动时校验
  • 因为它只计算配置，并不加载代码
一个 npm 包要成为 bundle，必须声明什么？
  • 在清单里声明一个字段指向补丁
  • 在导出里加一个浏览器侧的入口
  • 在依赖里列出宿主提供的能力包
  • 在打包清单里包含那个配置目录
