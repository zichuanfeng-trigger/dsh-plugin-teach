一树 · 层 · 行

tree 插件树

一次启动时，所有插件行按顺序拼出来的那整张表。它是运行期概念，不是某个文件。

怎么看见它：dsh --profile <名> --dump-config 把它完整打印成 YAML。

出处：docs/architecture.md · 本机实测

layer 层

树的一个来源单位。一个 bundle 贡献一层，一个 patch 文件也是一层。层有严格顺序，后叠的赢。

怎么认出来：dump 输出里的 # == <层名> 注释行。被改过的层会写成 # == A, patched by B。

出处：本机实测（见第一课第三节）

entry 行

树里的一条挂载记录，形如 - id: xxx / name: ... / config: ...。一行对应一个被挂载的插件模块，id 在整棵树里唯一。

本机 web profile 有 190 行，desktop profile 有 213 行。 本机实测

二profile · bundle · patch

profile 配置档

一个命名的组合，存在家目录里。它列出要叠的 bundle 顺序、存自己的补丁层、存装进来的插件依赖。

本机有 desktop（日常用，15 个 bundle）和 web（干净模板，2 个 bundle）。

出处：docs/architecture.md · 本机实测

bundle 组合包

一个 npm 包，package.json 里声明了 dsh.bundle.patch，指向它自己的一份 patch 文件。

判定标准只有这一条：有没有 dsh.bundle.patch。没有的包只是普通依赖，不算插件。

出处：@deepseek-ai/dsh-web-app/package.json 源码实读

patch 补丁

一份 YAML 数组，每个元素是一条动作。只有两种动作：- insert:（插入新行）和 - id: xxx + 字段（覆盖已存在的行）。

关键行为：覆盖时 config 是整体替换而非逐键合并。

出处：本机实测（第一课第四节）

三行与它的一行三件

字段是什么谁读它
id全树唯一的标识别的 patch 靠它定位要覆盖哪一行；插件管理器靠它开关某一项
name要挂载的模块名（或包名+子路径，或绝对路径）loader 用它去 import()
config传给插件的参数对象插件自己的 apply(ctx, config) 第二个参数
disabled是否挂载。布尔，或 !!js 表达式loader 在挂载那一刻判断
容易混的一点

package.json 里的 main 字段不参与挂载。挂载走的是 patch 里 name 写的那个路径。main 是给 pnpm 和其它工具看的。

四插件（plugin）

plugin 插件

一个 JS 模块，导出一个 apply 函数（或一个 Service 子类）。框架在挂载时调用 apply，把 ctx 交给它，它在 ctx 上注册能力。

最短的官方插件 @deepseek-ai/dsh-skill-badge 只有 53 行，第二课的标本。

出处：第一个插件（中文）

apply 入口函数

export function apply(ctx, config) {}。插件被挂载时调用一次；它返回的清理函数（若有）在卸载时调用。

C++ 类比：相当于插件必须实现的 IModuleInterface::StartupModule()。

五上下文（ctx）

ctx 上下文

传给 apply 的那个对象。它是服务的集合：你在它上面按名字找别的插件提供的能力，也在它上面注册自己的能力。

C++ 类比：一个服务定位器（service locator），不是一个基类。

常见子项：ctx.tools（工具注册表）、ctx.llm（模型层）、ctx.sessions（会话日志）、ctx.systemPrompt（提示词组装）、ctx.agents（活着的 Agent）。

出处：Cordis Primer

六服务（service）

service 服务

挂在 ctx.<key> 上的一个对象，代表一种能力。别的插件通过这个 key 找到它，而不是 import 具体实现。这就是「实现可替换」的机制。

C++ 类比：一个按字符串键查找的接口注册表，而不是编译期链接。

七依赖声明（inject）

inject 依赖声明

export const inject = ['tools']。声明本插件需要哪些服务。框架会等这些服务就绪才调用 apply，因此加载顺序不需要手写。

C++ 类比：模块依赖声明（Build.cs 里那个 PublicDependencyModuleNames），但由运行时保证先后，不是链接期。

出处：Cordis Primer · 源码实读（dsh-skill-badge/lib/index.js:47）

八效果（effect）

effect 可撤销效果

通过 ctx.effect() 或 ctx.on() 安装的注册。它们在插件卸载时自动撤销，不需要手动 removeListener / clearInterval。

从 ctx.effect 的回调里返回一个清理函数，框架在卸载时调用它。

出处：第一个插件 · 自动清理

九五种派发模式

模式是否等待顺序有返回值
emit否按注册顺序，只观察无
waterfall否按注册顺序，可包装有
parallel是全部并行无
serial是按注册顺序有
bail否按注册顺序，第一个返回值即停有

官方文档 出处：Cordis Primer · Dispatch Modes

waterfall 瀑布

「环绕式中间件」。监听器收到 (...args, next)：调 next() 就把（可能被包装过的）结果交给下一个；不调就直接短路，后面的监听器看不到。

C++ 类比：责任链 + 中间件，不是观察者。

DSH 里 agent/pre-step、agent/request、llm/stream、三个 tools/* 都是瀑布。

十Host 半部 · Client 半部

Host 宿主侧

跑在 DSH 进程（Node）里的那一半。apply(ctx) 在这里执行。工具、事件、服务都在这一侧。

入口：package.json 的 exports["."]（或 main 之外被 patch 的 name 指到的文件）。

Client 浏览器侧

跑在 Web 页面（浏览器）里的那一半。界面组件在这里。由 dsh.client 字段声明，入口是 exports["./client"]。

文件形态必须是 window.__ModuleLoader__.load({ id: "<包名>", factory(require) { ... } })。

出处：cordis-plugin-development/references/ui-plugin.md 本机内置技能

十一槽位（slot）

slot 槽位

界面上预留的「洞」，有名字。插件往洞里注册组件，而不是自己找位置插 DOM。

一个槽位有自己的 kind：single（只能一个占用者）/ list（可多个，按 order 排）/ keyed（按键分派）/ chain（条目自行提名）。

输入框相关的是 conversation.input.* 与 conversation.composer.dock。

出处：@deepseek-ai/dsh-client-ui-slots README 源码实读 · dialog-box/docs/06 dialog-box 调研

十二家目录与 profile 目录

路径是什么
~/.dsh/（$DSH_HOME）家目录。所有 profile、会话、技能都在下面。
~/.dsh/profiles/<名>/一个 profile 的目录。里面有 package.json（bundle 清单）、cordis.patch.yml（用户补丁层）、node_modules/（装进来的插件）。
~/.dsh/profiles/<名>/cordis.yml只有注释加一个 []。别改这个文件，改 cordis.patch.yml。

出处：本机实测 · dialog-box/docs/03
